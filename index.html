Glossary

Chord: multiple simultaneous events

Command: One programming instruction to tell limut what to do

Event: One event to be played; either an audio note/sample or a visual display

Expression: Code that evaluates to a value

Global Var: A variable; something whose value can be set by a command, and then read in an expression

Indicator: Visual display on the limut screen to help with composition or production

Map: Value containing multiple values indexed by keys

Modifier: Additional data thats changes the value of an expression, eg by modifying the current time it sees, or by providing a random seed

Param: A named parameter expression that controls the output produced by a synth

Pattern: A sequence defining the notes or control values to be played by a synth

Player: An player uses a synth to play events in a pattern, controlled by params

Subparam: An additional parameter provided extra info on how a param should control the output of a synth

Synth: An audio or visual synthesizer that can produce sound output or visual display.

Timevar: An expression whose value varies over time

Value: A primitive value to control synths

Indicators

Level VU meter for current output signal level. Use this when adjusting the output level, using either set main amp or the level slider, so it is just touching the red at its loudest. Only one active channel is shown if the mix is fully mono.

Beat Current audio system beat count, plus section info (current active section, count through active section, the current play out of the section's repeat if it has one, and next queued up section.

Timing Beat scheduling jitter: how late each beat fired compared to when it was due. This was previously labelled "Audio", but it is measured on the main thread along with the visuals, so it turns red when the browser cannot keep up with drawing and scheduling — not when the audio itself is too expensive. Heavy visuals, or something else on the machine such as screen recording, will turn this red while the synths are perfectly happy. There is no indicator for audio thread load because no browser API exposes it; to check whether the synths are the problem, type limutAudio.stats() in the browser console for the live count of audio worklet voices (superosc, chaos, pwm) — those are the most expensive things Limut can run, they all share a single audio thread no matter how many CPU cores the machine has, and superosc's unison multiplies the cost of every one of its notes.

Visual Visual lag; green when the framerate is keeping up to 60 fps; turns red when the system is struggling, which may lead to visual glitching

Limiter Audio limiter: turns red when the internal Limut limiter is active, implying the combined audio sources are too loud. Note this limiter is before the main amp control and vu meter, it makes sure the levels from individual synths do not go so loud as to distort. So if it is lighting up, lower the amp on individual synths, and if necessary, raise the main amp level to compensate.

Console

The console is the text window below the main code editing area. Use the console to see information, warnings and command output. Type a command and press enter to execute it.

list List all player base types, including presets, grouped by player base type and the include file that defined the preset

list audio List all player base types, filtered to those where the base type contains the given string

Collaboration

Limut supports live collaboration between two or more browsers using a peer-to-peer connection (WebRTC via peer.js). One peer acts as the server (host) and the others connect to it as clients. The server relays messages between connected clients so they all stay in sync. Connections are made directly between browsers; no Limut-specific server is involved, but a public peer.js signalling server and TURN relay are used to establish the connection.

Console commands

server Start hosting a session. The console will print a Peer session id; share that id with anyone who wants to join. The server's current code, run state, slider values, gamepad state and cursor are sent to each client when they connect.

server id Start hosting using id as the session id rather than a randomly assigned one. Useful for stable, memorable session names. The id must be unique on the peer.js network at the time the server starts.

connect id Connect to an existing session by its peer session id. On connect, the client receives the host's current code and run state and from then on stays synchronised.

connect id name Connect using name as your peer id rather than a randomly assigned one. Other peers will see this name in cursor labels, chat messages and connect/disconnect notifications. The name must be unique on the peer.js network.

say 'message' Send a short chat message to all connected peers. The message is shown in the console of each peer, prefixed with the sender's peer id. Quotes around the message are optional.

disconnect peer-id Server only: forcibly remove the named peer from the session. Useful when a peer has gone away without cleanly disconnecting (e.g. closed their browser or lost network) and the server still has the stale connection. Has no effect on clients.

What is shared

Code When a client connects, the host's current code is sent in full and replaces the client's code. After that, code edits made by any peer are sent as incremental changes and applied to all other peers in real-time. Either side can edit the code.

Run state Pressing run/stop on any peer starts or stops the code on all peers.

Cursors Each peer's text cursor position is shown as a coloured caret with their peer id as a label in every other peer's editor. Each peer is assigned a stable colour derived from their peer id.

Sliders Slider value changes (see the slider function) are broadcast to all peers, so every peer sees the same slider values.

Gamepads Gamepad axis and button state from each peer's locally connected gamepads is shared with every other peer. Remote gamepads are made available to gamepad functions alongside any local ones, so any peer's controller can drive the music.

Metronome The host periodically broadcasts its current beat time and bpm; clients gently slew their metronome to match, so all peers stay in time even if the host changes the bpm.

Chat The say command shares short text messages between peers in the console.

Notes

The connection is peer-to-peer and end-to-end between browsers; code and chat are not sent through any Limut-specific server. However, the public peer.js signalling server and a public TURN relay are used to establish and (if direct connection fails) relay the WebRTC connection.

Audio is rendered locally on each peer using their own synthesised output. The shared code, run state and metronome timing keep the audio in sync rather than streaming audio over the network.

If the host (server) disconnects, clients lose the session. Clients can disconnect and reconnect at any time without affecting the host or other clients.

Syntax Principles for Expressions

() Round brackets define chords in both patterns and expressions; that is, mutltiple events or values at the same time. Chord indexers and aggregators can be used to extract various values from chords.

[] Square brackets define sequences in both patterns and expressions; that is, multiple events or values one after another over time (sequences/timevars)

<> Angle brackets define higher level sequences in patterns; that is, a sequence where the next event is selected when the entire pattern repeats next.

{} Curly brackets in an expression supply extra information to a param (subparams), value (modifiers) or function call (arguments)

@ Defines the interval for an expression; that is, how often the expression should be evaluated within the event. Note, the interval applies directly to the nearest value. So for example, with this.foo@e the per-event @e interval will apply to the foo only. To force the overall this.foo lookup to be evaluated per event, you could use (this.foo)@e.

Commands

A command defines a player, preset or section, or sets player overrides, or sets global variables, or includes a limut source file. Commands may span multiple lines; a new command is started whenever the beginning of a command is recognised at the start of a new line. So any line that begins with one of the keywords include, set, preset or section, or with the id type pattern syntax for defining a player, will begin a new command.

Example: 

    include 'preset/synthwave.limut' // Command that includes a limut source file from a URL
    preset mysynth ping, amp=3       // Command that creates a preset synth based on the 'ping' synth, but overriding the amp value
    set bpm=130                      // Command that sets the global bpm (beats per minute) var to 130bpm.
    kick play x., amp=2,             // Start of a command that defines the player called 'kick', of type `play`, with an amp (volume) of 2
      drive=1/2                      // Continuation of the kick player definition, setting its drive param to 1/2
    set kick drive=0                 // New command defining an override for the kick player, setting its drive param to zero. Overrides like this take precedence over params set on the player itself.
    section drop, length=8           // Command that defines a section called 'drop', with a length of 8 beats. Players and vars can look up the current section and its params.

Defining a player

Basic structure: id synth pattern, params

A player command begins when something matching id synth pattern begins a new line. The params may follow on subsequent lines.

id Identifier for the player, so it can be referred to from other players etc. Must contain only alphanumeric characters from the basic Latin alphabet or underscore, and must not start with a digit. No player can be named set, preset, section or sx as those are reserved keywords.

synth Name of the audio or visual synth to use; eg piano

pattern Pattern of notes to play. Specifies the notes or sounds to play, and when to play them. Ends at the first comma; it can also be supplied (or overridden) as the pattern param instead, eg p ping 0, pattern=`0246`. A pattern param given by a preset is only a default, overridden by the pattern on the player line

params Comma separated list of params (eg amp=1/2) that affect how the player plays; see 'Value Syntax' and 'Params' sections below

Overriding player params:

Basic structure: set id params

A set overrides command begins when set begins a new line. The id and params may follow on subsequent lines.

id Player identifier; the override params will be apllied to this player. Can also be a list of multiple players to apply the params to; eg set (kd,sd) amp=0. Can include wildcards, so set p* ... will apply the overrides to every player whose name starts with 'p'. set * ... will apply to all players. set !p ... will apply to all players _except_ 'p'. It can also be the name of a section, or the section / sx keyword; see 'Overriding section params' below.

params Comma separated list of params (eg amp=1/2) that affect how the player plays; see 'Value Syntax' and 'Params' sections below

modification overrides params can be defined using operators to modify existing values rather than override them; eg add+=2 will increase the add parameter by an additional 2 on top of what it was already set to.

Setting global vars:

Basic structure: set var = value

A set global var command begins when set begins a new line. The var and value may follow on subsequent lines.

var variable to set; either a predefined var (see 'Predefined Vars' section below) or a user defined var which can be referenced from params on any player(s)

value expression value to set; see 'Value Syntax'

Creating a synth preset:

Basic structure: preset name synth, params

A preset global var command begins when preset begins a new line. The params may follow on subsequent lines.

name The name for the preset. The preset can be used by players by referring to this name as the player type. Must contain only alphanumeric characters from the basic Latin alphabet or underscore, and must not start with a digit.

synth The existing synth (or preset) to base this preset on

params Series of param overrides to apply for players that use this preset

Including a limut source file:

Basic structure: include 'url'

Include a limut source file. The file will be downloaded from the given URL and then executed as limut code. The file will only be downloaded once, but will be executed every time the code is updated.

url The URL of the limut source file to include. Must be in single quotes as a limut string. Include standard limut libraries from eg 'preset/synthwave.limut'. Include limut source from anywhere on the web (CORS permitting) using the full URL; eg 'https://sdclibbery.github.io/limut/preset/synthwave.limut'

Defining a section:

Basic structure: section name, params

Sections describe the large scale structure of a piece (intro, build, drop, breakdown etc). A section is just a named bag of params that is active for a span of beats. Players and vars can look up those params (see 'Lookup examples' below) so that the whole piece can respond to which section is currently playing and how far through it we are.

A section command begins when section name begins a new line, optionally followed by a comma and params. The params may follow on subsequent lines.

name The name for the section, used to refer to it from set section.next / set section.active and from param lookups (eg drop.riser). Must contain only alphanumeric characters from the basic Latin alphabet or underscore, and must not start with a digit.

params Comma separated list of params (eg riser=[0:1]l16@f), evaluated the same way as player params. Any param can be looked up from the section; see 'Value Syntax' below.

Compound assignments work here just as they do for player params, combining with the param's default value: section drop, length*=2 gives a section twice the default length (64 beats), and section drop, length=8, length+=4 gives 12. They combine with the default (not with the section's previous definition) so re-running the code leaves the value unchanged.

length The length of the section in beats. Defaults to 32. When the active section has been playing for this many beats it ends and the next section starts. May be an expression involving random or time vars, eg section drop, length=[4,8]r; it is evaluated when the section becomes active and held for that whole run (all its repeats).

next The name of the section to queue when this section becomes active, eg section verse, next=chorus. This lets each section declare its own successor, so the piece sequences itself; if two sections name each other (verse→chorus, chorus→verse) they alternate indefinitely. An explicit set section.next=name still overrides the declared next. Besides a bare name it can be an expression that evaluates to a section name (a bare name evaluates to its own text), eg next=(chorus,verse)r queues a random one of the two, chosen afresh each time the section becomes active.

repeat The number of times the section plays before advancing to next, eg section verse, length=8, repeat=4, next=chorus plays verse four times (32 beats) then moves to chorus. Each repeat replays from the top (so time/riser/fall reset), while section-scoped block players keep sounding continuously. With no repeat the section plays once. Like length, it may be a random/time-var expression (eg repeat=[1,3]r), evaluated once when the section becomes active.

Standard section functions:

Every section (including the built in default) automatically defines these functions, so you can drive players and vars off which section is playing and how far through it we are without any extra setup. Look them up with section.name (the active section) or drop.name (a named section). sx is a short alias for section, so sx.riser is the same as section.riser. You can override any of them by giving the section a param of the same name.

active 1 when the section is the active section, 0 otherwise.

in Alias for active.

exists 1 for any section that has been defined, 0 otherwise (eg drop.exists).

time The number of beats elapsed through the section, starting at 0. 0 when the section is not active.

rtime The inverse of time: the number of beats remaining, counting down from the section length to 0 at its end. Equal to the section length when the section is not active.

riser Ramps from 0 at the start of the section to 1 at its end. 0 when the section is not active.

rise Alias for riser.

fall Ramps from 1 at the start of the section to 0 at its end. 1 when the section is not active.

count Which repeat of the section is currently playing, counting from 0. Resets to 0 when the section becomes active and increases by 1 each time it reaches its length. Handy with repeat, eg section.count==section.repeat-1 is 1 on the final repeat. 0 when the section is not active.

Overriding section params:

Basic structure: set name params

Section params can be overridden after the fact, exactly as player params are: set drop length=4, set drop riser*=2, set drop foo=3. Any param works, including length, repeat and next, and including params the section never declared. Modification overrides combine with the section's value (or with its default if it has none), so set drop length*=2 doubles the declared length. The built in default section can be overridden the same way, eg set default length=4.

Overrides are read live, so unlike a length expression — which is fixed when the section becomes active — changing a set line takes effect as soon as you update the code, even part way through the section. Like player overrides, they only last as long as the line is in the code: remove it and the section goes back to its declared value.

set section params (or set sx params) overrides whichever section is currently active rather than a named one, matching how section.riser reads the active section. If a section also has an override by name, the keyword one is applied on top of it.

If a player and a section share a name, the player wins and the override applies to the player — the same precedence param lookups use, where drop.amp reads the player drop if there is one. Wildcards (set p* ...) only ever match players.

set drop next=chorus follows the same rules as the expression form of next rather than the bare name on the section line, so a var of that name would be resolved first; set drop next=(chorus,verse)r works as you would expect.

Section-scoped code:

Block structure: 

    section drop {
      set p* vel=0
      f perc f, vel=drop.riser^3
    }, length=16

A section can carry a block of code lines that are only active while it is the active section. Open the block with { at the end of the section line, put ordinary commands (players, set overrides and vars, presets) on their own lines inside it, and close it with } at the start of a line, optionally followed by a comma and the section's params. Sections cannot be defined inside a block.

Whenever the active section changes, the code is automatically re-run: lines in the newly active section's block take effect, and lines in every other section's block are ignored. Players defined in a block are created when their section starts and removed when it ends (like deleting the line and updating), so the same player id can be given a different definition in different sections. set overrides in a block only apply while the section is active. The section itself (its length, next and other params) is always defined regardless of which section is active; only the block lines are conditional.

set section.active=name and set section.next=name lines are ignored during these automatic re-runs (otherwise they would refire on every section change); they still apply on a normal code update.

Section timing:

There is always exactly one active section. Before you define or select any section, a built in default section (length 8) is active and repeats forever, so section param lookups always resolve. The default section is an ordinary section: you can redefine it like any other — give it a length, params, a next, or a section default { ... } code block — and refer to it by name (default.riser, set section.next=default). Redefining it with no explicit length keeps its 8 beat default; remove the redefinition and it reverts to the built in baseline.

When the active section reaches its length, playback advances to the queued next section (or back to the default section if none is queued) — unless it has a repeat and has not yet played that many times, in which case it replays instead. Queuing a next section consumes it; once it becomes active there is again no next queued, so unless you queue another the piece falls back to the default section after it.

The readout in the top bar shows the active section, how many beats into it we are, its length, and the next section; eg drop 5/16 -> default. When the section has a repeat it also shows the current play, eg drop 5/16 (2/4) -> default.

Triggering a section:

Below the readout is a row of buttons, one per defined section, which is the easiest way to trigger a section while performing. Click a button to queue that section as the next one, so it starts when the current section reaches its length; click it again to unqueue it. Shift click to switch to the section immediately. The button of the section that is playing is highlighted, and the queued one is outlined. The row only appears once you have defined a section of your own; with just the built in default section there is nothing to choose between.

Clicking is usually preferable to putting set section.next=name in the code, because the code lines are re-run every time you update the code, so they re-trigger the section on every update until you comment them out again. A button click happens exactly once.

Patterns

x-o- Sequence of events, each with duration given by the player's dur param, for use with play

0123 Sequence of events, each with duration given by the player's dur param, for use with tonal synths. Numbers are scale degrees

`01 23` Pattern literal; inside backticks, pattern elements can be separated by whitespace which will be ignored. Backticks force the contents to be treated as a literal, so for example `01 loop 1` is treated as the literal 01loop1 and the loop operator is ignored. Double quotes are an equivalent delimiter, so "01 23" means the same thing; use double quotes when the pattern is itself inside a backtick pattern param, eg pattern=`"01 23" + "45 67"`

0-1-2-3 Negative scale degrees allow tones below the synth root pitch

x. Use a dot for a rest

0# # following numeric event makes it sharp

0b b following numeric event makes it flat

0= = following numeric event extends the duration by 50%

0! ! following numeric event shortens the duration by 33%

0^ ^ following numeric event makes it 50% louder

0v v following numeric event makes it 33% quieter

0a Other characters following numeric event become params; for example t tri 01g23, glide=this.g/2

x^ ^ following non-numeric event makes it 50% louder (for use with play synth)

0_[_1] Continuation: use underscore to extend the previous note duration. Currently continuations are not valid within chords () or supersequences <>

0[123] Subsequence: square brackets to fit multiple events into one dur (triplet shown)

0(135) Chord: Round brackets to play multiple events together

0<12> Supersequence: angle brackets to play events in sequence as the pattern repeats. Eg 0<12> is exactly equivalent to 0102

01 loop 2 Restrict the number of times the pattern can loop. In the example, the pattern 01 will play twice and then stop. The player will not reset until it gets recreated or changed. So if a player with a loop pattern has finished its repeats, it will not start playing again until it is commented out/in, or playback stopped and restarted, or the pattern string is changed and updated.

0123 crop 2 Crop a pattern to a given number of steps. For example, 0123 crop 2 is equivalent to 01. Crop will repeat the pattern if necessary, eg 01 crop 5 is equivalent to 01010

1 + 2 Concatenate two patterns; the first pattern plays then the second. For example, 12 + 34 is the same as 1234

1 * 2 Repeat a pattern; the first pattern plays a given number of times. For example, 12 * 2 is the same as 1212

now 01 Play the pattern starting on the next beat, rather than as if it had been playing from beat 0. In the example, the pattern 0123 will play starting from the 0 whatever beat the player is started on.

follow p1 Use follow to follow another player (named 'p1' in the example) pattern

gamepad Use gamepad to generate notes from a gamepad controller rather than a pattern. The gamepad buttons will be mapped to note degrees in some arbitrary way.

gamepad 1 use input from gamepad 1 (default is 0)

gamepad lt:vel Use the left trigger (assumed to be analogue) to control the given param (vel for velocity of the gamepad notes). When the lt: arg is used, the left trigger will not play a note itself.

gamepad rt:echo Use the right trigger (assumed to be analogue) to control the given param (echo in the example). When the rt: arg is used, the right trigger will not play a note itself.

gamepad nodpad On some controllers the dpad can be in the way of the sticks. Using 'nodpad' will disable the dpad input.

Values

Basic structure value{modifiers}@interval

Note: the order of interval and modifier can be swapped if desired. For example, []r@f{seed:1} is the same as []r{seed:1}@f.

value Actual value (which may include subparameters); see below

{modifiers} Map of modifiers and/or arguments. Modifiers may modify the time passed to the value expression, or the value it returns, or provide additional data for a parameter. For example, [1,2,3]t1{0:0,per:8} will give a sequence that repeats every 8 beats, forced to the value 0 at the start of each repeat. In other words, the repeating sequence: 0,2,3,1,2,3,1,2. See "Modifiers" below.

@interval Intervals specify how often the value should be evaluated, for example once per event (then the same value through the event), or continuously varying. See "Intervals" below.

Values:

1 Single, constant numeric value

0dB Numeric values can be expressed in dB. But while scroll=6dB is still the same as scroll=2, it doesn't make much sense to write it way (especially since it is impossible to express negative numbers with dB: Eg -20dB is the same as 1/2. 1s Time in seconds

1000ms Time in milliseconds

1Hz Frequency in Hertz (cycles per second). Also 1cps is the same as 1Hz and 1kHz is 1000Hz.

(1,2) A chord. Multiple values, all played together at the same time

[1,2] Sequence of values, one after another, one per event in the pattern, ignoring rests. For single length patterns only, all values will be expanded, so p ping 0, add=[0,1,2] will cycle through all three values.

[] Equivalent to [0,1].

[1,2]t3 Timed sequence, each value lasts for 3 beats. Duration must be a const number, cannot be an expression. Default time unit: beats.

[]t Equivalent to [0,1]t.

[1:12,2:4]t Timed sequence with variable timing per value. Durations can be expressions. Default time unit: beats.

[0:3]t1 Timed sequence, expanded. The example is equivalent to [0,1,2,3]t1

[1,2]l3 Timed linear interpolated sequence, each value takes 3 beats to change into the next. Default time unit: beats.

[]l Equivalent to [0,1]l.

[1:12,2:4]l Timed linear interpolated sequence with variable timing per value. Durations can be expressions. Default time unit: beats.

[1,2]s3 Timed smooth interpolated sequence, each value takes 3 beats to change into the next, using an 's' shaped ease in/out curve. Duration must be a const number, cannot be an expression. Default time unit: beats.

[]s Equivalent to [0,1]s.

[1:12,2:4]s Timed smooth interpolated sequence with variable timing per value. Durations can be expressions. Default time unit: beats.

[1,2]tx Section-relative timing. The x suffix makes the time used to index the sequence count from the start of the current section (see 'Sections') instead of from metronome time zero, so the sequence restarts at each section boundary. [1,2]tx and [1,2]xt are equivalent (the x may go on either side of the type letter). Supported for t, l, s, r and n (not e, which is already event-relative). For example lpf=[500,4000]tx sweeps relative to each section. Note: when no sections are defined the built-in default section (length 8, looping) is active, so x counts from each 8-beat boundary.

[1,2]e Timed interpolated sequence, each value is evenly spaced from beginning to end of the current event

[1,2]e1 Timed interpolated sequence starting at the beginning of the event, each value takes 1 beat to change to the next. Duration must be a const number, cannot be an expression. Default time unit: beats.

[0:!300ms,1:_[1/4b:1/2b]r,0]e Timed piecewise sequence starting at the beginning of the event. In this case it would provide an envelope for the event, with an exponential attack lasting 300ms, followed by a const sustain lasting between 1/4 and 1/2 a beat at random. Default time unit: beats.

[1:!200ms,0]e@s []e@s is the same as []e, except when used for an audioparam (eg amp or lpf), it will create segments instead of regular updates. This will provide more accurate and consistent timing (for example, for pluck envelopes). Note that if you add a per frame (@f) expression to an @s expression, the whole expression is evaluated per frame instead, so the @f part keeps updating (the @s part is then sampled per frame, losing its segment timing accuracy). Time modifiers still won't work correctly with @s.

[]r Select a different value every time, chosen randomly between 0 and 1

[1,4,7]r Select a different value every time, chosen randomly from the numbers 1, 4 and 7

[:9]r Select a different random float every time, between 0 and 9

[0:9]r Select a different random float every time, between 0 and 9. Note if this will be rounded to to an integer (eg for oct, add or sample params), then the upper limit is exclusive. eg oct=[2:3]r will give a float value between 2 and 2.9999...., so since oct rounds down to the nearest integer, it will always get oct=2

[0,1:7]r Select a different random float every time, either 0 or 1. The 1 is 7 times more likely than the 0.

[1,2]r4 Select a different value and hold for 4 beats, chosen randomly from the numbers 1, 2. The hold time must be a const number, it cannot be an expression. Default unit: beats.

[1:3]r{seed:1,per:4} Select a different determninistic random float every time, between 1 and 3; seed determines the random sequence; the sequence repeats every per beats. seed is also in beats, so adding 1 to seed pushes the sequence by 1 beat.

[]n Smoothly varying noise, moving between 0 and 1

[1:2]n Smoothly varying noise, moving between 1 and 2

[1:2]n4 Smoothly varying noise, moving between 1 and 2, taking 4 beats to progress from one value to another. The timing must be a const number, it cannot be an expression. Default time unit: beats.

[]n{seed:1,per:4} Smoothly varying deterministic noise, moving between 0 and 1; seed and per work the same as for []r

[ v1:i1t1, v2:i2t2, ... ]{p,repeat:0} Piecewise series. Allows interpolating between a set of values, specifying the interpolation and 'travel' between each pair of values, and allowing a custom parameter to control the interpolation. For example, [0:_1,1:\]{time*2} is controlled by double-speed time, starts at 0, stays constant at zero for 1 unit of double-speed time, then jumps to 1 and linearly falls back down to 0 for 1 unit of double-speed time.

v1 etc Expressions giving the values to interpolate between

i1 etc Interpolation operator

:/ :\ Linear interpolation operators; both do the same, but the two can be used to indicate direction

:_ Const interpolation operator: stay at original value right to end of step

:_ Step interpolation operator: immediately jump to new value from start of step

:~ Smoothed interpolation operator: bezier ease in/out s-shaped smooth transition through step

:! Exponential interpolation operator: exponential growth/decay to target

:^4: Power interpolation operator: power curve interpolation. In this example, the interpolation is raised to power 4, so it will move slowly to start with the quickly reach the target. :^1/4: would quickly move toward the target, then slow down.

t1 etc The amount of parameter p travel between this value and the next; note the sequence wraps round. Default time unit: beats.

p Parameter expression giving the current point of travel through the piecewise series

repeat Optional repeat parameter. Leave out for a repeating pattern, set to zero to disable repeat and clamp the value when the parameter is less than zero or greater than the full length of the piecewise.

vN: A trailing colon with no size on the last value is shorthand for repeat:0; the final value holds forever instead of the series repeating. For example [1:\2,3:]{x} is equivalent to [1:\2,3]{x,repeat:0}: it ramps 1 to 3 over 2 units then stays at 3. A redundant trailing step operator with no size (vN:_) works the same way, since a step on the final value just means "stay here"; so [1:\8,2:_]{x} is equivalent to [1:\8,2:]{x}. Other trailing interpolators (eg linear \) still repeat.

[v1,v2]:iN A default interpolator/size written after the bracket applies to every segment that doesn't specify its own; per-segment specs override it field by field. For example [1,2]:_8{x} is equivalent to [1:_8,2:_8]{x}, and [1,2:/4]:_8{x} is equivalent to [1:_8,2:/4]{x}. Interpolator and size default independently, so [1,2:4]:_8{x} is equivalent to [1:_8,2:_4]{x}.

+ Add values together; eg [2,3]+4 is equivalent to [6,7]

- Subtract values; eg [2,3]-1 is equivalent to [1,2]

- Unary minus operator; eg -[1,2] is equivalent to [-1,-2]

/ Divide values; eg [1,2,3]/2

* Multiply values; eg [1,2,3]*1000

% Take remainder; eg (0,4,7,9)%7 is equivalent to (0,4,0,2)

^ Raise to the power; eg 2^3 is 8. Imaginary results return 0; eg -1^1/2 returns 0.

| Concatenate chords; eg 1|2 is the same as (1,2), and (1,2)|(3,4) is (1,2,3,4)

?? "If then" operator. Check a condition in the left operand for truthiness, and return either the value in the right operand, or nothing. Eg this.foo??5 will return nothing if this.foo is (eg) 0, or 5 if this.foo is (eg) 1. This operator short circuits, so if the right operand is not returned, it will not be evaluated. Where the condition is a visual node it compiles into the shader instead; see the visual synth section.

?: "Or else" operator. If the left operand is nothing, return the right hand operand. Otherwise, return the left operand. Eg this.foo?:5 will give the value of this.foo if present, or 5 if not. Note this can be used with the above ?? operator as a ternary conditional expression; eg this.foo>1 ?? 2 ?: 3 - if this.foo is greater than 1, then the expression will evaluate to 2, otherwise it will evaluate to 3. This operator short circuits, so if the right operand is not returned, it will not be evaluated. As with ??, a visual node condition compiles into the shader instead; see the visual synth section.

< Check if the left operand is less than the right. Returns 1 if left is less, 0 if not.

> Check if the left operand is greater than the right. Returns 1 if left is greater, 0 if not.

<= Check if the left operand is less than or equal to the right. Returns 1 if left is less or equal, 0 if not.

>= Check if the left operand is greater than or equal to the right. Returns 1 if left is greater or equal, 0 if not.

{2,y:1} Map, containing keys and values, with a main value of 2. The main value is the same as if no map was used; eg chop={2,wave:'tri'} is the same as chop=2, but also supplies an additional 'wave' subparameter.

Intervals:

@e Use @e to evaluate this value once per event

@f Use @f to evaluate once per frame (60 times a second). For example lpf=[300:3000]l8@f will update the lpf cutoff frequency continuously, while lpf=[300:3000]l8 will be evaluated only once for each event played.

@s Use @s to evaluate per segment for audio param control. This is more accurate for audio envelopes. For example, amp=[1:!200ms,0]e@f will evaluate 60 times per second which may give an inconsistent and sloppy envelope. But amp=[1:!200ms,0]e@s will create a single exponential audioparam segment giving a more accurate result. Mixing @s and @f in one expression is fine: the whole expression falls back to per frame evaluation so both parts keep updating for the life of the event. This works whether the @f is added alongside the @s (eg lpf=100+300*([10:!1,0]e@s+[]l1@f)) or nested inside the @s timevar (eg lpf=100+300*([10:!1,[]l1@f]e@s)).

User Defined Functions

Basic structure: {args} -> body

User defined functions (also called lambdas) let you build reusable expressions. The {args} declares the parameters, and the expression after -> is the function body. Functions are values like any other, so they are usually stored in a global var with set and then called by name.

Defining a function

set double = {value} -> value*2 Define a function called double with one argument called value, which returns the argument doubled.

set square = {x} -> x^2 Argument names can be anything; they are referenced by name inside the body.

set add = {x,y} -> x+y Multiple arguments are separated by commas.

set hello = {} -> 'hi' A function with no arguments still needs the empty {} on the left.

set lpf = {freq, q:5} -> biquad{'lowpass', freq:freq, q:q} Arguments can have default values using name:default. If the caller does not supply that argument, the default is used. Arguments without a default are required.

Calling a function

double{3} Call with a single positional argument. Returns 6.

add{3,4} Call with multiple positional arguments. Returns 7.

add{x:3,y:4} Call with named arguments. Order does not matter; add{y:4,x:3} gives the same result.

add{3,y:4} Positional and named arguments can be mixed.

hello{} No-argument calls can optionally include the {}

hello A user function can still be called without an arg list.

Piping with >>

3>>double The >> operator feeds the value on its left into the call on its right as its first argument, so this is double{3}. Any positional arguments already at the callsite shift up a place, so 3>>add{4} is add{3,4}.

3>>double>>add{1} Piping reads left to right in the order things happen, which is a lot clearer to read and quicker to edit while performing than the equivalent nested calls (add{double{3},1}).

set scaled = {in, by:2} -> in*by A function meant to be piped into should declare the piped value as its first argument, so that 4>>scaled{3} gives 12.

(1.7).floor{1/2} The . operator passes its left side in exactly the same way when the right side is a call with an argument list. It binds tightest where >> binds loosest, so it suits a single call inside a larger expression.

Node functions are the exception: for them >> connects audio rather than passing arguments, so osc{}>>lpf{500} wires the oscillator into the filter as it always has. The same applies whenever the value on the left is already an audio node, so effects built as user functions still connect: shifter{3/4}>>reverb{1b}.

Positional argument names

Positional arguments are looked up by the names value, value1, value2 etc, in order. So {value,value1} -> value*value1 can be called as foo{3,4} to get 12. This means that the first argument name value is special: if you declare {value} -> ... then the first positional arg fills value, and you can also pass it by name as foo{value:3}.

A consequence is that a function with a first argument named value can be called very concisely. This is how many library functions (for example mix2, echo, and the shapers in lib/nodes.limut) accept their main argument positionally without the caller writing any name.

Inline (anonymous) functions

({x} -> x^2){3} A function can be called immediately without storing it in a var, by wrapping the definition in round brackets and applying arguments. Returns 9.

convolver{{x} -> (1-x)^3, length:1s} Anonymous functions are often passed directly as arguments to other functions (for example to node functions such as convolver and shaper) to provide a shape or envelope.

set twice = {f,x} -> f{f{x}} An argument that holds a function can itself be called with arguments inside the body. For example twice{{v}->v*2, 3} returns 12. This allows wrapper functions around node functions like parallel, for example set wrapped = {chain,count} -> parallel{{i}->chain{i}, count} (the library multiband function is built this way).

Scope and global vars

Inside a function body, argument names take priority over global vars with the same name. So in {foo} -> foo, the foo in the body refers to the argument, not to any global var called foo.

global.foo Use the global. prefix inside a function body to force a lookup of the global var, bypassing any argument of the same name. For example {foo} -> global.foo ignores the passed argument and returns the global foo.

Global vars that are not shadowed by an argument are visible inside the body as normal. So set gain = 2 followed by set amp = {x} -> x*gain will multiply x by whatever gain is when amp is called.

What a function can return

The body is a normal expression, so it can return anything an expression can produce: numbers, chords, timevars, maps, strings, or audio node chains. For example {freq} -> osc{'sine', freq:freq} returns an audio node; {} -> []r@f returns a per-frame random value. Interval markers (@e, @f, @s) inside the body carry through to the caller as expected.

Passing a timevar as an argument works naturally: double{[4,5]t1@f} evaluates the timevar on each frame and doubles each value.

Examples

set clamp = {x, lo:0, hi:1} -> min{max{x,lo},hi} Define, then call as clamp{0.7}, clamp{1.5, hi:2}, etc.

set mix2 = {chain} -> mix{chain, 1/2} A thin wrapper around a node function (as used in lib/nodes.limut).

set echo = {time:1/8b, feedback:0.7, max} -> delay{time, feedback:feedback, max:max??max?:time*2} A library effect built from the delay node function (as used in lib/effects.limut).

Audio Synths

! / stop / none

Base synths

audiosynth Base type with no defined audionode graph. The play param takes an audionode graph for each note. Note the player freq param is predefined for this player type as the note pitch derived from the pattern and other usual player params (add, oct, scale etc).

bus Audio mix bus. Plays continuously, can take a pattern but the pattern is ignored. As a result, all bus param values are evaluated per frame. Chords and []e are not valid for bus players. Audio players can use the bus param to choose which bus to mix into (by id). A bus player does not have pitch effects (addc, vib etc), but does have wave effects (compress, drive, fold etc). There is an implicit bus called main that exists at all times, and provides the final mix for all other players and buses. Overrides can be used to set params on the main bus; eg set main echo=1/2. There is also an implicit silent bus that exists at all times with amp=0: anything routed into it (bus=silent) is inaudible, but its .pre tap still carries the full summed signal — use it to make a player heard only as a modulator via .pre.

external take audio from microphone or line in. Use the track param to specify the track within the stream. If the input signal appears on only one stereo channel (or you only want the signal from one stereo channel), use the channel param to select the channel and force it to mono.

track=1 Select which audio track to use from the input.

channel=1 Select a single audio channel to use from the input.

wave1={'saw',amp:[0:1]n,detune:wow} The main value is a string giving the waveform to use. amp is a per frame amplitude control. detune is a per frame detune control in semitones.

unison=1 Number of detuned voices (1 to 16) layered together for a supersaw-style sound, with a detune subparam (eg unison={7, detune:1.02}) giving the max frequency ratio the voices are detuned by. The voices are spread evenly (geometrically, ie by pitch) each side of the primary frequency: the outermost sit at freq*detune and freq/detune, the centre at the primary. The interior voices are nudged slightly off that perfectly even spacing, since exactly-even detuning makes the voices periodically re-converge in phase (an audible pulsing) — the nudge keeps the sound an evolving shimmer instead. detune defaults to 1.01 (a subtle detune) when unison is above 1. An amp subparam (eg unison={7, amp:2}) sets the ratio of the centre voice's amplitude to the outermost voices' (default 1 = all equal, above 1 for a stronger centre, below 1 for a scooped centre); voices in between are weighted smoothly, and overall loudness is held roughly constant. A pan subparam (eg unison={7, pan:1/2}) sets the stereo width the voices spread across: the outermost voices sit at pan to each side (so pan=1/2 runs them from 50% left to 50% right, pan=1 hard left to hard right), the centre voice stays centred, and pan=0 stacks them all in the middle. Defaults to 0.5. Note: audio render cost scales with the number of voices.

visualsynth Build a visual from a chain of visual nodes, compiled into a single shader. Set the px param to a node chain connected with >>; eg px=mul{2}>>tex{webcam{}}. Every pixel starts as its own coordinate (a 4-component vector with xy set), which flows left to right through each node in the chain; the final value is the pixel colour (rgba). Node params may be timevars etc, and update every frame; eg px=mul{[]n4}>>tex{webcam{}}. The node chain is the whole shader: in-shader params like zoom, recol, pixellate, fore and back do not apply, though non-shader params (loc, blend, dur etc) still work.

Operators work on visual nodes, and compile into the shader too. Arithmetic (+ - * / % ^) applies to all 4 components; eg px=mul{1}/2+#080. Where both sides of an operator are visual nodes they each see the same incoming value, and their results are combined; eg px=tex{'a.png'}+tex{'b.png'}. Comparisons (< > == etc) give 1 or 0 per component, which is handy for thresholding; eg px=id>0.5. Note that >> binds looser than arithmetic, so px=id/2>>tex{webcam{}} is (id/2)>>tex{webcam{}}.

The conditional operators work on visual nodes too, so ?? and ?: give a px chain a ternary: px=length<1/2 ?? #f00 ?: #00f is a red disc on a blue ground. A shader has no branches, so this compiles into a blend between the two sides rather than taking one path — which means both sides are always evaluated, unlike the scalar operators, which short circuit. The test is against zero, as it is for a scalar (so any non zero value is true, negative included) — which makes a comparison the natural thing to condition on, since it already gives 1 or 0. Write > 0 where you mean a sign test rather than relying on truthiness. The edge is hard by construction: use smoothstep and mix{} where you want it antialiased.

The choice is made per component, testing each channel of the condition separately, so a condition with different values per channel picks a different side for each: px=#f00 ?? #ff0 ?: #00f takes yellow's red and blue's green and blue, giving #f0f. Usually that does not come up, because a comparison of two single values, or a channel read like id.x, gives the same value in all four channels and so acts as one condition for the whole pixel. Where you do want a single condition out of a colour, reduce it to one value first, eg dot{id,#3b1}>1/2.

With no ?: the false side is whatever is coming down the chain, the same way mix{b,t} takes its dry side from there — so px=tex{webcam{}}>>(id.r>1/2 ?? #f00) reddens the bright pixels and leaves the rest of the image alone. That mirrors the scalar meaning, where ?? on its own gives nothing, and nothing in a chain means leave the value as it was. Note the brackets there: >> binds tighter than ??, so without them the whole chain would be read as the condition. Conditions can be chained as else-ifs, since ?: takes another conditional on its right: px=id.x<0 ?? #f00 ?: id.y<0 ?? #0f0 ?: #00f gives three regions, and the first matching one wins as it does for scalars.

An arithmetic expression is a chain segment like any other, so the call at its head is handed the incoming value in the same way: px=floor{1/8}+1/2 means the same as px=floor{1/8}>>add{1/2}, and px=sin*#0f0 the same as px=sin>>mul{#0f0}. Only the head of the expression takes it, so px=id/2+floor{1/8} adds a constant (the head there is id, which already has what it needs); write px=id/2+floor{id,1/8} for the other reading.

The maths functions work on visual nodes too, and compile into the shader: floor, ceil, round, fract, abs, sign (sgn), min, max, clamp, smoothstep, sqrt, exp, pow, the vector ones dot, cross, length and normalize, the hashes pxhash and pxhashf, and the trig functions sin, cos, tan, tanh, atan. Give one a visual node as an argument and you get a visual node back; every other argument becomes an animatable param as usual. All of them apply to each of the 4 components. Because >> pipes its left side in as the first argument, they chain naturally: px=floor{1/40}>>tex{webcam{}} quantises the coordinates into 1/40 blocks before sampling, ie pixellation. The argument form does the same thing where a chain is awkward, eg px=abs{sin{id*4}}.

A chain always starts with the incoming pixel value, so a call at the head of one is handed it without being asked: px=floor{1/40} floors the pixel coordinate. Where a call already holds a visual node of its own it keeps its arguments as written, so the argument form still means what it says (px=abs{sin{id*4}} is the absolute value of that sine, not of the coordinate). id is the name for that incoming value, for using it inside an expression — px=id/2+#080, px=dot{id,#3b1}, px=id>0.5 — and writing px=id>>X means exactly the same as px=X. A px that is a plain value rather than a chain fills the whole quad with it, so px=#f00 is a flat red.

Where id is the value arriving at that point of the chain, uv is the value the chain started with — the pixel coordinate, still there after nodes further up have replaced what is flowing through. That is what lets a coordinate be used on a colour: px=perlin2>>mul{y:uv.v/2+1/2} fades a noise field out towards the bottom of the screen, where a bare id there would be the noise value rather than the coordinate. The coordinates run −1 to 1 vertically with y up (and wider than that horizontally, by the aspect ratio), so uv.v/2+1/2 is the way to write a 0 to 1 ramp. At the head of a chain uv and id are the same thing.

All of which means visual nodes can be built up as user defined functions, taking their input as the first argument: set pixellate = {in,size:8} -> floor{in+(0.5/size),to:1/size}, then px=pixellate{40}>>tex{webcam{}}. Similarly set monochrome = {in,v:1} -> mix{dot{in,#3b1},v}, then px=tex{webcam{}}>>monochrome{[]l1@f}. A user defined function is a segment of the chain rather than a new chain, so the incoming value arrives both as its first argument and as the value flowing into whatever its body builds; that is why mix{} above finds it as its dry side without being handed it.

Visual nodes: id is the incoming value, for naming it inside an expression, and uv the value the whole chain started with; mul{} multiplies each component by its param, add{} adds its param to each component and set{} forces components to its param; channels{} runs an expression of its own on each channel; tex{} samples a texture (a url string, or a texture source like webcam{}) at the incoming xy; mix{} blends between two values; pxhash{} gives a random value per pixel.

The four channels of the value flowing down the chain can be named as coordinates (x y z w), as colours (r g b a) or as texture coordinates (u v, or GLSL's own s t p q) — the same four channels either way, just spelt to suit what you are doing. Note w always means the fourth channel, so the third texture coordinate is p. mul{}, add{} and set{} take channels either as subparams (add{y:1/4}) or as a vector or colour param (add{{y:1/4}}, set{#.f..}), each of which animates on its own, and any channel the param does not name is left untouched; eg px=add{v:1/4}>>tex{webcam{}} shifts the image vertically without touching the other channels. Where a channel wants a whole expression rather than a value, channels{} takes one per channel.

Channels can also be read back off a visual node with ., which is how you rearrange them. One channel on its own comes back in all four, so it behaves like a number: in.v is the second channel everywhere. Several at once are taken in the order you write them, leaving the channels you did not name as they were: in.vu swaps the texture coordinates and in.bgr swaps red and blue, both keeping alpha. Since a channel read is itself a visual node it can be given straight back to set{}, add{} or mul{} as a channel's value, which is the long hand of the same thing.

So a user defined function is all it takes to remap channels; eg set swap = {in} -> in.vu, then px=swap>>tex{webcam{}} transposes the camera, and so does the spelt out set swap = {in} -> set{u:in.v, v:in.u}. Colours work the same way: set bgr = {in} -> in.bgr, then px=tex{webcam{}}>>bgr. With the maths functions there too, a rotation of the texture coordinates is just its own definition (in radians, as sin and cos are): set rot = {in,a} -> set{u:in.u*cos{a}-in.v*sin{a}, v:in.u*sin{a}+in.v*cos{a}}, then px=rot{[0:6.283]l8}>>tex{webcam{}} spins the image once every 8 beats. Note that a name that is a function wins over a channel read, so tex{}.abs is still the abs function rather than the a, b and s channels.

uv The value the whole px chain started with: the pixel coordinate, y up, running −1 to 1 vertically and wider than that horizontally by the aspect ratio. Unlike id, which is whatever is arriving at that point of the chain, uv still means the coordinates however far down the chain it is used — so px=tex{webcam{}}>>mul{uv.v/2+1/2} darkens the camera towards the bottom of the screen, and px=perlin2>>mul{y:uv.v/2+1/2} fades a noise field the same way. It is a visual node like any other, so channel reads and arithmetic work on it (uv.v, uv.vu, uv.v/2+1/2, length{uv}). It keeps meaning the whole chain's coordinates inside a channels{} argument and inside a user defined visual function, which is where it earns its keep: in px=perlin2>>channels{g: id*uv.v}, id is that one channel and uv is still the coordinate. At the head of a chain it is the same as id, and X>>uv throws away whatever X made and gives the coordinates back.

mul{value} Multiply each channel of the incoming value by the param (a number applies to all channels; a vector like {x:2,y:1}, or the subparam form mul{x:2,y:1}, applies per channel and leaves the channels it does not name alone). The param can be another visual node, in which case it is multiplied in per pixel; eg px=tex{webcam{}}>>mul{tex{'mask.png'}}.

add{value} Add the param to each channel of the incoming value (a number applies to all channels; a vector like {x:0.1}, or the subparam form add{x:0.1}, applies per channel and leaves the channels it does not name alone). Useful for offsetting coordinates before a tex{}, or brightening a colour after one; eg px=tex{webcam{}}>>add{[0:1/2]l4}. With no param it adds nothing.

set{value} Force channels of the incoming value to the param, leaving the rest untouched. Use it to force a colour channel after a tex{}, eg px=tex{webcam{}}>>set{#.f..} forces green fully on; or to pin a texture coordinate before one, eg px=set{u:1/2}>>tex{webcam{}} samples the same column for every pixel. As with add and mul, channels can be named as subparams (set{u:1/2,v:0}) or given as a vector or colour; a param naming no channels at all (a plain number) replaces all four. A channel's value can be another visual node rather than a number, which is what makes channel swaps work: set{u:in.v, v:in.u}. With no param it does nothing. Note that a three digit colour literal always carries an alpha, so set{#.f.} forces alpha to 1 as well; use the four digit set{#.f..} to leave alpha as it was.

channels{a,b,c,d} Split the incoming value into its four channels, run an expression of its own on each, and put them back together; eg px=channels{sin{id*1},sin{id*2},sin{id*3}} gives each channel a different sine mapping. Arguments are taken in channel order, or named (channels{r:id^2, b:1-id}) as they are for set{}; a channel with no expression of its own passes through untouched, so px=tex{webcam{}}>>channels{tex1d{{x}->{h:x}}} maps the red channel through a hue sweep and leaves green, blue and alpha alone. Each channel arrives as a single value in all four components, so id inside an expression means that one channel whichever way you spell it, and the matching component of the result is what comes back out. Each argument is a px chain in its own right, so everything px can say it can say too: a call at its head takes the channel without being handed it (channels{sin, cos}), >> and arithmetic work as usual (channels{floor{1/8}+1/2}), and a plain value is just that value (channels{1/2}, animating as any other param does).

mix{a,b,t} Blend between two values: t of 0 gives a, 1 gives b, and in between it interpolates each channel. With only two args the first value is the one coming down the chain, so mix{b,t} blends the incoming value towards b, the same shape as the audio mix{} node; eg px=tex{webcam{}}>>mix{dot{id,#3b1},1/2} is half desaturated, and so is set monochrome = {in,v:1} -> mix{dot{in,#3b1},v} used as px=tex{webcam{}}>>monochrome{1/2}. The mix amount can be named (mix{b, mix:1/4}) and defaults to 1/2. Any of the three can be a visual node, so a texture or a pattern can act as a per pixel mask; eg px=mix{#f00,#00f,tex{'mask.png'}}.

pxhash{value,seed} A random value per pixel: a hash of the incoming value, so px=pxhash is white noise. It is a hash rather than a random generator, meaning the same incoming value always gives the same result — which is what makes it useful. Quantise the coordinates first for bigger grain, eg px=floor{1/8}>>pxhash gives blocky noise, and px=pxhash{id*3} hashes a scaled copy of them. Red, green and blue get independent random values in 0 to 1 and the incoming alpha is kept, so noise comes out opaque and using it as a multiplier cannot make an image see through; use channels{a:pxhash} where a random alpha is what you want. With no seed the field is the same every frame and every event; give one (named, or as the second positional arg, eg px=pxhash{seed:2}) to pick a different field, and animate it for moving noise, eg px=pxhash{seed:[]l} is TV static. Note that plain rand gives a single value for the whole quad, not one per pixel. As a param it must be handed the value explicitly, since params are not piped the way a chain is: px=tex{webcam{}}>>mul{pxhash{id}}, not mul{pxhash}.

pxhashf{value,seed} As pxhash, but a cheaper hash (a sine based one, avoiding the 32 bit integer multiplies pxhash uses, which are slow on some GPUs). On ordinary px values the two are hard to tell apart. It gives up two things: the pattern depends on the driver's sin, so the same line gives different (though equally random) noise on different GPUs, where pxhash is identical everywhere; and being floating point its distribution decays once the incoming value or the seed grows large, so heavily scaled coordinates or a long running animated seed will start to band where pxhash keeps going. Prefer pxhash unless you have measured a difference: pxhashf is around twice the speed, but on an M1 that is a saving of about 0.17ms on a full 4K pass (0.04ms at 1080p), so it only starts to matter with many hashes per pixel at high resolution.

Smooth noise is built out of all this rather than being a node of its own: include 'lib/visual.limut' (or lib/everything.limut) gives you value noise (noise1, noise2, noise3), perlin gradient noise (perlin1…perlin3, and the signed perlin1s…perlin3s) and the octave sums fbm2, fbm3 and turb2 — eg px=noise2{scale:16} or px=fbm2>>tex1d{{x}->{labh:x}}. See the Visual Library section for the details; being written as ordinary user defined functions, it is also a worked example of what a chain of visual nodes can say.

Shapes are built the same way: include 'lib/sdf.limut' gives you circles, boxes, triangles, polygons, stars, hearts and the rest as signed distance fields, along with ways to combine them and draw them — eg px=sdstar{r:3/4}>>sdfill. See the SDF Library section.

tex{source} Sample a texture at the incoming value's xy. The source may be an image url string (eg tex{'favicon-32x32.png'}) or a webcam (eg tex{webcam{'5mp'}}).

tex1d{f} Look the incoming value up in a lookup texture generated by sampling a limut expression. f is called with a single argument running from 0 to 1, and whatever it gives back (a number for a grey, or a colour in any of the usual forms) becomes that point of the map; the incoming value's x (ie r) channel then indexes it. Use it for palettes, gradients and recolouring, eg px=tex{webcam{}}>>tex1d{{x}->{labh:x}} maps camera brightness through a sweep of lab hues. Anything can go in the expression, so piecewises make gradients: px=tex1d{{x}->[#f00:\1/2,#00f:\1/2,#f00]{x}}. The size subparam sets the number of texels (default 256).

tex2d{f} As tex1d, but a two dimensional map: f takes two arguments, each running from 0 to 1, and the incoming value's xy indexes it; eg px=tex2d{{x,y}->{r:x,g:y}}. Default size 64 (ie 64x64 texels).

tex3d{f} As tex1d, but a three dimensional map, indexed by the incoming xyz — ie a colour cube, the usual shape for a full colour grade. f takes three arguments; eg px=tex{webcam{}}>>tex3d{{r,g,b}->{r:b,g:g,b:r}} swaps red and blue. Default size 16 (ie 16x16x16 texels); note the cost is the cube of the size, so keep it small.

All three are sampled once and kept: editing the line rebuilds the map, but a slider or timevar inside the expression is frozen at the value it had when the map was built. Any number of texture nodes can be used in one chain, so px=tex{webcam{}}>>tex1d{{x}->{h:x}} and px=tex{'a.png'}+tex{'b.png'} both work.

webcam{device} Webcam texture source for tex{}. The device param is an index or part of the device label string, as for the webcam visual synth; width/height set the ideal camera resolution.

webcam Display video feed from the attached webcam (if present). The browser will ask permission before allowing access to the webcam. Use the device param to sepcify the device as an index into the list of devices, or as part of the device label string (defaults to index 0). When a webcam synth is first used, the console will log the available devices and their indexes and labels. Use the width and height params to specify your ideal camera resolution (defaults to 640x480).

device Device index or part of the device label string.

xor Bitwise xor with mod, giving changing pixellated patterns

Common Event Params

amp Player amplitude control. For audio players, this defaults to the event vel so that velocity controls the player volume.

delay Event start time offset. Default time units: beats. Once applied, delay is removed from the event so it is not visible to expressions via this.delay or player.delay.

delay={1/2,add:2} subparams on delay will be used to override the event values. In the example given, the add param of the delayed event will be set to 2, but any params can be overridden this way. This is most useful with chords of delay values, as it allows individual delayed events to change their properties.

dur Pattern step duration. Timevars, random vars and index vars can be used to give variation in duration. Chords cannot be used with the dur param. Default time units: beats.

pattern Pattern to play, replacing the pattern given on the player line; eg p ping 0, pattern=`0246`. The value is a string, so backticks (or quotes) are required, and the full pattern syntax including the pattern operators can be used, eg set p pattern=`0123 crop 3`. Because the pattern given on the player line is delimited by the first comma, this is also the way to use a pattern containing a comma.

The pattern param is evaluated once per beat, so it can be a timevar, a random var, or a var lookup, allowing the pattern itself to change as the player plays; eg set p pattern=[`0246`,`1357`]t8 alternates between two patterns every 8 beats. A changed pattern stays aligned to the beat grid, just as it does when you edit the pattern on the player line; use now (eg pattern=`now 0246`) to restart it from the beginning instead.

The pattern given on the player line is itself the pattern param, layered over the preset and under the player's own params. So a pattern param from a preset acts as a default that the player line pattern overrides, a pattern param on the player line overrides both, and a set override wins over all of them. For example with preset foo readout, pattern=`123`, the player r foo 456 plays 456 while r foo plays the preset's 123. Compound operators combine with the player line pattern, so p ping 01, pattern+=`23` plays 0123.

Only players that play a pattern use this param, so it has no effect on follow, midi, gamepad and keyboard players, or on continuous players such as bus and the visual synths.

quantise Snap event count to a grid of the given size, in beats. Eg quantise=1/4 snaps events to the nearest 1/16-note grid point. Applied after stutter so stuttered events can be quantised. If snapping back would put the event in the past, it is pushed forward to the next grid slot instead. Set to 0 to disable.

rate Playback rate for 'play' samples, animation rate for visuals

stutter Split each event into multiple events spaced evenly within the same time period. Eg with stutter=2, an event starting at time 0 with a duration of 1 will be split into two events of duration 1/2, starting at 0 and 1/2. Stutter of 0 or 1 has no effect and is the default. Stutter is rounded down to the nearest integer value. Once applied, stutter is removed from the event so it is not visible to expressions via this.stutter or player.stutter.

stutter={2,dur:1/4} the dur subparam forces the time between stutter events rather than dividing the original event's duration evenly. Default time units: beats, eg stutter={2,dur:1/4s} for quarter-second spacing.

Any other subparam can be supplied and will be applied to the extra stutter events only — the first event keeps its original params. Eg stutter={2,amp:1/4} plays the first note at normal amp and the second at amp=1/4, useful for echo-like tails.

A user defined function can be supplied to control each stutter event individually, receiving the stutter index (0-based) and returning a map of param overrides. The lambda is applied to every stutter event including the first. Eg stutter={4,{i}->{oct:2+i}} plays 4 notes per pattern event with octaves 2, 3, 4 and 5.

sus Sustain time. Note the 'sustain' in an ADSR envelope sets the sustain level, however this param sets the sustain time. The default is time required after attack and decay to take the note to the end of the duration. Default time units: beats.

swing Amount to swing alternating 1/4 beats, as a Linn LM-1 style percentage from 50 (no swing) to 66 (perfect triplet swing) to 75 (maximum dotted note swing). You can set swing for all players at once using (eg) set * swing=60

swing={66,period:1/2} The period to apply the swing. Defaults to 1/4 of a beat (suitable for house music).

Read only params

exists READ ONLY param. One if the player is defined, even if its not currently playing any event.

idx READ ONLY param. The pattern index of this event. The pattern index counts through the pattern, then resets when the pattern repeats.

player READ ONLY param. The name of the player currently playing. For a follow player, will be the name of the follow player (not the player it's following).

playing READ ONLY param. One if the player exists and is currently playing one or more events.

pulse READ ONLY param. A value that rises and falls as a note plays on the player. If multiple notes are playing, the value will be a chord. The value is pre-multiplied by the note velocity (the vel param).

time READ ONLY param. The current time in beats this event has been playing for.

voice READ ONLY param. This param is set to the voice index of an individual event within a chord. So for example: p ping 0, add=(0,2). Here, there are two events within the chord, with add values of 0 and 2. The voice values for these events will be 0 and 1, since the voice increments. This can be used to change other values based on the voice index within the chord.

Audio Params

add Amount to add onto event scale degree, in degrees. Evaluated per event only.

add={0,#:1} Sharpen the scale degree (add a given number of semitones)

add={0,b:1} Flatten the scale degree (subtract a given number of semitones)

addc Amount to add onto event pitch, in semitones. Evaluated per frame, and accepts fractional values, so addc=[0:12]e will slide the note from the starting pitch smoothly up a whole octave over the course of the note.

apf1 All pass filter frequency. Default time units: Hertz. Multiple allpass filters can be specified with params apf1, apf2 etc. They will operate in parallel so their outputs sum, allowing phase cancellation.

apf={400,q:2} Allpass filter resonance. Default: 1.

att Attack time. Default time units: beats.

bits bit crush effect; value is number of bits. 1 bit is very distorted to (eg) 32 bits is relatively clean. 0 disables the effect.

bits={12,gain:2} Input gain; gain amp to apply to the signal before bits is applied

bits={1,mix:1/4} Mix subparam controls dry/wet mix. 0 for dry only, 1 for wet only. default: 1

bpf Band pass filter frequency. Default time units: Hertz.

bpf={400,q:20} Band pass filter resonance. Default: 1.

bpf={400,poles:4} Filter poles. Default is a 2 pole filter giving 12 dB/octave. Alternatively, specify 4 for a Moog-like 4 pole filter giving 24 dB/octave.

bpf1 Multiple, parallel bandpass filters are available using params bpf1, bpf2 etc.

bus id of the bus that this player should mix to. If the sepcified player does not exist, this player will be silent. If the bus param is not specified, this player will be mixed to the global main bus.

choke Set a choke group. Notes played with a choke group will cut off other notes that are already playing if they have the same choke group. The choke group can be a string, and can apply across multiple players.

chop Apply a tremolo effect that chops the audio signal, eg chop=2cpb chops the signal twice per beat. Default time units: cycles per beat

chop={2,wave:triangle} chops twice per beat with a triangle waveform. The default waveform is sine; the options are sine, square, triangle, saw.

chop={4,mix:1/4} Mix subparam controls dry/wet mix. 0 for dry only, 1 for wet only. default: 1

chorus Strength of lfo-delay based stereo chorus effect.

chorus={1,mix:1/4} Mix subparam controls dry/wet mix. 0 for dry only, 1 for wet only. default: 1

clip boost the signal then apply hard clipping

clip={12,gain:2} Input gain; gain amp to apply to the signal before clip is applied

clip={1,mix:1/4} Mix subparam controls dry/wet mix. 0 for dry only, 1 for wet only. default: 1

compress Compression ratio, or the reduction in volume for signals above the compression threshold. A ratio of zero disables compression.

compress={12,gain:2} Input gain; gain amp to apply to the signal before compression is applied

compress={12,threshold:-40dB} Threshold at which the compression ratio kicks in. Default is -50dB

compress={12,knee:10dB} the 'knee' is a softening of the compression curve, so that there is no sudden changeover at the threshold. A value of 0dB disables the knee and gives a sudden changeover. Other values are the range over which the knee should apply. Default is 40dB.

compress={12,att:0.1} Compressor attack time. The attack time is the time it takes for compression to 'kick in' once a signal crosses the threshold. Default is 0.01 (or 10ms). Default time units: seconds.

compress={12,rel:0.2} Compressor release time. The release time is the time it takes for compression to 'go away' once a signal falls back below the threshold. Default is 0.25. Default time units: seconds.

dec Decay time. Default time units: beats.

detune Amount of detune in semitones

drive overdrive by boosting the signal then applying soft clipping. Low values (eg 1/32, 1/16) give a gentle overdrive. Mid values (eg 1/8, 1/4) give a distortion effect. Higher values (eg 1/2, 1) give a full on fuzz.

drive={12,gain:2} Input gain; gain amp to apply to the signal before drive is applied

drive={1,mix:1/4} Mix subparam controls dry/wet mix. 0 for dry only, 1 for wet only. default: 1

echo Echo time delay. Default time unit: beats.

echo={1,feedback:0.8} Echo feedback gain, 0 to 1, default 0.35. Higher value means the echo persists for longer.

echo={1,max:2} Echo max time delay. Only valid for bus echo. The bus echo time can be varied, but cannot be larger than this. Defaults to either 1 beat, or the initial value of the delay time, whichever is larger. Default time unit: beats.

envelope Specify the envelope type to use: 'full' (ADSR), 'simple' (ADR), 'organ' (ASR full volume while on like an organ), 'pad' (uses a cosine roll on/off so consecutive notes maintain constant volume), 'linpad' (uses a linear roll on/off, a better crossfade when the source is identical (including phase) between events), 'percussion' (R - instant attack). Or, specify an envelope directly as an expression, for example envelope=[1:!300ms,0]e@s

flanger LFO frequency for flanger effect. Default time units: cycles per beat.

flanger={1/3,mix:1/4} Mix subparam controls dry/wet mix. 0 for dry only, 1 for wet only. default: 1

fold distort the signal by boosting then folding the overdriven part of the waveform

fold={12,gain:2} Input gain; gain amp to apply to the signal before fold is applied

fold={1,mix:1/4} Mix subparam controls dry/wet mix. 0 for dry only, 1 for wet only. default: 1

glide Glide from one note to the next (portamento). When a note plays with glide set, if there is a previous note playing on the same player in the same voice, then both notes will glide in pitch from the old note's pitch to the new. glide=1/3 means it takes 1/3 of a beat to glide from the old note to the new. Default value is 0 (no glide). Default time units: beats.

glide={1/3,curve:4} glide curve. Zero means no curve, or a linear frequency change. Positive curve means the frequency moves quickly to the target, then slows down as it approaches. Default is 1.

high High shelf gain. Eg high=-6dB will act like a gain of 1/2 for the high frequencies. Must specify the value with the dB unit, or use a relative gain value instead.

high={-8db,freq:400} High shelf cutoff frequency. Default: 1100Hz. Default units: Hertz

hpf High pass filter frequency. Default time units: Hertz

hpf={400,q:20} High pass filter resonance. Default: 5.

hpf={400,poles:4} Filter poles. Default is a 2 pole filter giving 12 dB/octave. Alternatively, specify 4 for a Moog-like 4 pole filter giving 24 dB/octave.

low Low shelf gain. Eg low=-6dB will act like a gain of 1/2 for the low frequencies. Must specify the value with the dB unit, or use a relative gain value instead.

low={-8db,freq:400} Low shelf cutoff frequency. Default: 200Hz. Default units: Hertz

lpf Low pass filter frequency. Default time units: Hertz

lpf={400,q:20} Low pass filter resonance. 10 is approximately the transition where resonance starts to kick in. Default: 5.

lpf={400,poles:4} Filter poles. Default is a 2 pole filter giving 12 dB/octave. Alternatively, specify 4 for a Moog-like 4 pole filter giving 24 dB/octave.

mid Mid gain. Eg mid=-6dB will act like a gain of 1/2 for the mid frequencies. Must specify the value with the dB unit, or use a relative gain value instead.

mid={-8db,freq:400} Mid cutoff frequency. Default: 600Hz. Default units: Hertz

mid={-8db,q:10} Mid q defines the width of the mid frequency band; low q is wide. Default: 5

mono Force a signal to mono: the input signal appears equally in both left and right channels

nf Notch filter frequency. Default time units: Hertz

chaos{freq:440, type:lorenz, chaos:0.5, axis:x, smooth:0, seed:0} Create an AudioWorklet-based chaos oscillator source node: a strange-attractor / chaotic-map generator that emits a deterministic-but-non-repeating signal, inspired by Serum's chaos oscillators. Because it is a real audio node it works as both a control-rate LFO and an audio-rate modulator through the same mechanism — use it in a param expression and it connects straight into the target: lpf{ 400 + chaos{freq:6}*300 } is a slow, non-repeating filter wobble, while osc{ freq: 110 + chaos{110}*40 } is organic FM. wt=0 Morph position across the wavetable's frames (0..1), lerping between adjacent frames.

A negative sync keeps the same ratio magnitude but softens the phase reset with a short crossfade (a "soft sync"), for a less clicky, less aggressive tone.

crush=0 Phase-quantisation amount in bits (0 = off): the phase (after any sync remap) is snapped to 2^crush steps before the wavetable lookup, stepping the waveform for a lo-fi/aliased timbre, so crush=3 gives 8 steps and each extra bit doubles the resolution (max 12).

pwm=0 Phase power-warp amount (0 = off): the phase (after any sync remap) is raised to the power 2^pwm before the wavetable lookup, skewing the waveform toward its start (pwm>0) or end (pwm<0) like a generalised pulse width.

formant=0 Formant-warp shift (0 = off): the waveform (after any sync remap) is resampled within each cycle at 2^formant times the rate (wrapped, with the band-limiting span scaled to match) and multiplied by a raised-cosine window over the fundamental phase, so the cycle length (the pitch) is preserved while the spectral formants shift up (formant>0) or down (formant<0) for a vowel-like timbre, à la Serum/Vital's formant warp.

The output is mono unless the note has 2 or more voices and a non-zero pan, so single-voice or un-panned notes keep the downstream chain mono.

tts{'hello', rate:1, pitch:50, speed:175} Create a text-to-speech source node that synthesizes the given text to speech and plays it through a buffer source, so speech can be wired into an fx chain like any other source, eg tts{'hello world'} >> lpf{800}. Voice options (pitch 0–99, speed words per minute, wordgap, amplitude 0–200, variant eg 'f2') tune the synthesized audio; rate changes playback speed/pitch like a sample. Unlike sample it does not loop by default. A first-use phrase is synthesized in the background and starts as soon as it is ready; repeated phrases are cached.

Visual Library

Visual library: include 'lib/visual.limut'

This library contains smooth noise and a colour palette for visualsynth px chains. It is written entirely as user defined functions built out of the visual nodes — pxhash for the randomness, floor/fract for the lattice, smoothstep for the fade curve and mix for the interpolation — so it is worth reading as a worked example of what a chain of visual nodes can say. Nothing in it is implemented in javascript.

Noise

pxhash on its own gives an independent random value per pixel, ie white noise. Smooth noise instead hashes the corners of a lattice cell and interpolates between them, so neighbouring pixels get neighbouring values. Value noise interpolates the corner values themselves; perlin (gradient) noise interpolates a random gradient at each corner, which looks less blocky and is naturally signed.

All of them share the same three arguments. The first is the incoming px value, so they pipe like any other chain segment (px=fbm2 and px=id>>fbm2 are the same thing) and can equally be handed a value of their own (px=noise2{id*8}). scale is how many lattice cells the coordinate space is divided into, defaulting to 4 because the incoming coordinate only spans about -1 to 1. seed picks a different field, and animating it gives noise that churns. As these are user defined functions, all arguments can be positional.

The 1, 2 and 3 suffixes are how many dimensions the noise varies over, not how many channels come out: every one gives a single value in all four channels, as the maths functions do. The 3d ones take their third dimension from the incoming z, which is zero unless you put something there — drive it off a timevar for noise that moves in place rather than one that scrolls past. Note that two plain user function calls back to back (px=noise2>>colourise) evaluates the head as a scalar; put a node function or an explicit id>> between them.

noise1{in, scale:4, seed:0} One dimensional value noise, 0 to 1, varying along x only: a smooth random ramp, so px=noise1{scale:8} is soft vertical bands. Useful as a slowly wandering value to drive something else with.

noise2{in, scale:4, seed:0} Two dimensional value noise, 0 to 1. The workhorse: px=noise2{scale:16} is a soft grey cloud field. Compare px=pxhash (white noise) and px=floor{1/8}>>pxhash (blocky noise) to see what the interpolation buys.

noise3{in, scale:4, seed:0} Three dimensional value noise, 0 to 1, taking its third dimension from the incoming z. With z left at zero it is identical to noise2; drive z to move through the field, eg px=noise3{id>>set{z:[]l8}} churns rather than scrolls.

perlin1{in, scale:4, seed:0}, perlin2{in, scale:4, seed:0}, perlin3{in, scale:4, seed:0} Gradient (perlin) noise in 1, 2 and 3 dimensions, shifted and clamped into 0 to 1. Less blocky than value noise, since it is the gradients rather than the values that are randomised, so it has no extrema pinned to the lattice points.

perlin1s{in, scale:4, seed:0}, perlin2s{in, scale:4, seed:0}, perlin3s{in, scale:4, seed:0} The signed forms of the same, roughly -1 to 1 and centred on zero, which is what displacing a coordinate wants: px=add{perlin2s{id,8}/4}>>tex{webcam{}} warps the image. The plain perlin functions are these scaled into 0 to 1 for display.

fbm2{in, scale:4, seed:0} Fractional brownian motion: four octaves of noise2, each at twice the frequency and half the amplitude, summed and normalised back to 0 to 1. The extra octaves add fine detail on top of the broad shapes, which is what makes noise look like cloud or terrain rather than blur: px=fbm2>>tex1d{{x}->{labh:x}}.

fbm3{in, scale:4, seed:0} As fbm2 but over noise3, so it animates through the incoming z: px=fbm3{id>>set{z:[]l8}} is a rolling cloud.

turb2{in, scale:4, seed:0} Turbulence: the same octave sum over the absolute value of each signed octave, which creases the noise at every zero crossing instead of smoothing through it. Gives the billowy, veined look that suits smoke and marble.

There is no loop construct in a px chain, so the octaves are written out as four terms rather than iterated. Copy the definition and add or drop terms for more or fewer octaves, remembering to fix up the divisor, which is simply their weights summed.

Internals, should you want to build your own: noiseface{i,f,seed} is one square of value noise (the four corner hashes of lattice cell i interpolated by the already faded fractional position f), perlingrad{i,d,o,seed} is one corner's gradient contribution and perlinface{i,d,f,seed} the square of them, and noiseflat1/noiseflat2/noiseflat3 scale the incoming value and flatten the channels the noise does not vary over (a lattice point must hash the same all the way along them).

Colour

cospal{in, d:#012, c:#fff, b:#888, a:#888} A cosine palette, after Inigo Quilez: a single value in becomes a smoothly cycling colour out, so it is the cheap way to colour a noise field or a distance field. It is simply a+b*cos{6.28318*(c*in+d)}, and because those four are colours rather than plain numbers each channel gets its own cosine — which is what makes it a palette rather than a grey ramp. a is the level the colours swing about, b how far they swing, c how many cycles the incoming 0 to 1 covers and d the phase, ie where in the cycle 0 lands. Compared with tex1d it builds no lookup texture (just three cosines) and its arguments stay live rather than being frozen when the map is baked, so they can be animated.

It wants a single value in, so pipe it something that gives one: px=fbm2>>cospal colours a cloud field and px=length>>cospal is a set of concentric rings, or hand it one, as px=cospal{id.x} does to sweep the palette across the screen. Given the raw coordinate bare, px=cospal runs red off x, green off y and blue off nothing, which is a plaid rather than a palette. The defaults are cream at 0, through orange and brown to near black at 1/2, then pale blue and back to cream: the small #012 phase spread is what tilts one half of the cycle warm and the other cool, and #888 being a shade over half means the peaks clip, giving small flat highlights.

The arguments come in reverse order after in — d, then c, b, a — so the phase, the one most worth reaching for, is the first positional: px=fbm2>>cospal{#05a} spreads the channels a third of a cycle apart for a full rainbow, where cospal{#000} leaves them in phase for a plain grey ramp. Name the others, eg cospal{c:#248} gives each channel a different number of cycles so they beat against each other rather than tracking together, and cospal{b:#444} keeps the whole thing near mid grey. Colour literals are hex digits out of 15, so #fff is one and #888 is 8/15.

The cosine runs on all four channels, alpha included, so the palette drives transparency along with colour. That shows up nowhere by itself, since the canvas is opaque and a plain visual does not blend, but if you are layering with blend set then >>set{a:1} after it keeps the result solid.

SDF Library

Signed distance field library: include 'lib/sdf.limut'

Shapes for visualsynth px chains, converted into limut from the GLSL on Inigo Quilez's 2d distance functions page. As with the Visual Library, everything here is an ordinary user defined function built out of the visual nodes; nothing is implemented in javascript.

A signed distance field gives, for every pixel, the distance to the nearest edge of a shape: negative inside, zero on the edge, positive outside. A shape here is therefore not a picture but a number per pixel, and drawing it is a separate step. That is what makes the shapes worth having: a distance can be thresholded into a fill, or its absolute value thresholded into an outline; subtracting from it rounds every corner at once; and the smaller of two distances is their union, so shapes combine with plain arithmetic rather than needing to be drawn on top of one another.

v1 visualsynth, px=sdcircle{r:1/2}>>sdfill
v1 visualsynth, px=sdstar{r:3/4}>>sdbands
v1 visualsynth, px=sdbox{b:{x:3/4,y:1/8}}>>sdannular{1/32}>>sdfill{#0f0}

Every shape takes the incoming px value as its first argument, so they pipe like any other chain segment and can equally be handed a coordinate of their own (px=sdcircle{id*2, 1/4}). The coordinate has y up and runs from -1 to 1 vertically, and wider than that horizontally by the aspect ratio of the frame, so a radius is a fraction of half the frame height and circles come out round rather than stretched. Distances are in those same units.

Since the incoming value is the first argument, a positional argument only lands where you expect when the call is being piped one: px=sdcircle{1/2} at the head of a chain is a radius of 1/2, but the same call nested as an argument (px=sdfill{sdcircle{1/2}}) reads the 1/2 as the coordinate instead. Name the arguments (sdcircle{r:1/2}) or pass the coordinate yourself (sdcircle{id, 1/2}) wherever the shape is not at the head of a chain. The same applies to the noise functions in the Visual Library.

Shapes

sdcircle{in, r:1/2} Circle of radius r. Just length{in}-r, and the only shape whose field is exact everywhere.

sdbox{in, b:1/2} Rectangle of half extents b, ie b is the distance from the middle to an edge, not the width. A plain number gives a square (sdbox{b:1/2}); a vector gives a rectangle (sdbox{b:{x:3/4,y:1/8}}).

sdsegment{in, ax:-1/2, ay:0, bx:1/2, by:0} Distance to the straight line between the points ax,ay and bx,by. A line has no inside, so the distance is never negative and this one wants sdround to become visible: px=sdsegment{ax:-3/4, ay:-1/2, bx:3/4, by:1/2}>>sdround{1/16}>>sdfill draws a stroke of half width 1/16 with round ends.

sdtriangle{in, r:1/2} Equilateral triangle of radius r, pointing up.

sdpentagon{in, r:1/2}, sdhexagon{in, r:1/2} Regular pentagon and hexagon, r being the distance from the middle to the flat of an edge. The pentagon points up; the hexagon has flat top and bottom and points left and right.

sdstar{in, r:1/2, n:5, m:10/3} Regular star with n points of radius r. m is how deeply the notches between the points are cut, and runs from 2, where the edges are flat and the shape is simply a regular n sided polygon, up to n, where the notches reach the middle and the points are needles. It need not be a whole number, and the default of a shade over 3 is what makes the default five pointed star the familiar one. Animating it is the obvious move: px=sdstar{r:3/4, m:[2:5]l4}>>sdfill.

sdheart{in, r:1/2} Heart of half height r.

sdcross{in, arm:1/2, thick:1/6, r:0} Greek cross (a plus sign) with arms of half length arm and half thickness thick. r rounds the corners, inner ones included, without growing the shape.

sdcirclewave{in, tb:1/2, ra:1/4} A wave of semicircular arcs of radius ra repeating endlessly along x, centred on the origin. tb is how much of each circle is used, from nearly 0 (a flat line of shallow scallops) through 1/2 (half circles, ie a proper wave) to 1 (whole circles strung together). Like sdsegment it is a line rather than a region, so give it an sdround or sdannular to see: px=sdcirclewave{tb:[0:1]l8, ra:1/4}>>sdround{1/64}>>sdfill.

To move a shape, shift the coordinate going into it, which moves it the other way: px=add{x:1/2}>>sdcircle{r:1/4}>>sdfill puts the circle half a frame to the left. Dividing the coordinate scales it up, though the distance comes back scaled to match, which only matters if you then round or blend it.

Combining

Union and intersection are simply min{} and max{} of two distances, which already work on visual nodes, so there is nothing here for those: px=min{sdcircle{r:1/3}, sdbox{b:{x:3/4,y:1/8}}}>>sdfill is a circle with a bar through it. All of these take the distance as their first argument, so they pipe.

sdround{d, r:1/16} Round off every corner by r. It also grows the shape by r in every direction, which is what turns a line into a stroke of that half width.

sdannular{d, w:1/32} Hollow the shape out into an outline of half thickness w. Unlike sdstroke below this gives back a distance field rather than a colour, so the outline can go on being combined with other shapes.

sdsub{a, b} Cut shape b out of shape a; eg px=sdsub{sdbox{b:1/2}, sdcircle{r:1/3}}>>sdfill is a square with a round hole.

sdblend{a, b, k:1/8} Union with a smooth blend of width k, so that the two shapes flow into one another rather than crossing, the way drops of liquid do. The distance is only approximate near the join.

Drawing

A distance rendered as it stands is a grey ramp, so these turn one into a picture. Each takes the distance as its first argument, so it can be piped one (sdcircle{r:1/2}>>sdfill) or called around it (sdfill{sdcircle{r:1/2}}). soft is the width of the antialiasing ramp across the edge; raise it for a deliberately soft edge, and note that it is in coordinate units rather than pixels, so a shape scaled right down wants a smaller one.

sdfill{d, col:#fff, bg:#000, soft:0.01} Fill the inside with col and the outside with bg.

sdstroke{d, w:0.01, col:#fff, bg:#000, soft:0.01} Draw the edge only, w either side of it.

sdbands{d, outside:#e93, inside:#adf, k:6, n:150, soft:0.01} Inigo Quilez's own way of showing a distance field, and the one used for the pictures on his page: one colour inside and another outside, both fading with distance and banded with concentric stripes, with the zero isoline picked out in white. Worth reaching for while building up a shape, since it shows the whole field rather than only where it changes sign. k is how fast the fade is and n how many bands.

Colouring is not limited to these: a distance is a single value in all four channels, so anything that maps one value to a colour will take it, eg px=sdstar{r:3/4}>>cospal or px=sdheart{r:3/4}>>tex1d{{x}->{labh:x}}.

Internals, should you want to add a shape of your own: sdflat{in} flattens the incoming value to a 2d point (z and w must be zero, since length and dot work on xyz), sdvec{a,b} builds a 2d point back up out of two computed values, sdval{v} splats one channel across all four the way the maths functions do, and sdstep{v} is 0 below zero and 1 above. Those first three are what the shader shape of all this forces: there is nowhere to put a local variable, so intermediate results are passed on to a helper function instead. Every if in the original becomes the ternary, eg q.x + 1.7320508*q.y > 0 ?? sdvec{…} ?: q for the fold in sdtriangle, which blends between both results rather than taking one path. sdfold{p,n} mirrors the plane about a line through the origin, which is how one edge of a polygon is made to stand for all of them.

303 library: include 'preset/303.limut'
Audio

tb303 Simulated 303 (acid) bass. The following custom control params are available, corresponding to the main control knobs on a 303:

wave 303 waveform. set to 'saw' or 'square'. The default is 'saw'.

cutoff 303 cutoff control 0 to 1; default 1/2. Set the filter cutoff. Higher values give a brighter sound with more harmonics. Note vel is not automatically included in cutoff for the 303 because cutoff is very specific in the 303.

resonance 303 resonance control 0 to 1; default 1/2. Set the filter resonance. Higher values give a squelchy acid sound.

envmod 303 envmod control 0 to 1; default 1/2. Set the depth of envelope modulation. Higher values change the filter cutoff more over the course of a single note.

decay 303 decay control 0 to 1; default 1/2. Set the envelope decay time. Set the envelope decay time for filter envelope. Higher values take longer to decay.

accent 303 accent control 0 to 1; default 1/2. Set how much effect accented notes have.

The following pattern flags can be used:

a accent flag. Makes the preceding note accented, making it louder and brighter.

u up octave. Makes the preceding note an octave higher.

d down octave. Makes the preceding note an octave lower.

s slide. This does not (yet) work the same as the 303 slide, which would slide the _next_ note from this one, and not retrigger the envelope for it. However currently in the limut 303, it slides the _current_ note, and the envelope still retriggers (no legato).

For exampple b tb303 0u0d0ua0 plays a pattern of four notes, one up an octave, the next down an octave, one up an octave and accented, then one without any flags.
